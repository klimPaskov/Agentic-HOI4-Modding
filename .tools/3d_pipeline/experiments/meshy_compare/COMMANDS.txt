STEP 0. PREREQUISITES (all free; items marked DECISION need the maintainer)

0.1 DECISION. A Setup build whose launcher accepts the 0.6.7 runtime.
    The installed C:/Users/klimp/AppData/Local/HOI4 Mod Setup/hoi4-mod-setup.exe (30,493,184 bytes,
    2026-10-31 18:16) embeds the runtime folder name for 0.6.2, not 0.6.7. HOI4-Mod-Setup main has
    the 0.6.7 pin (commit 584c317, PR #135, 2026-11-01 19:15) under "Unreleased"; the newest tag
    is v0.8.2 and was cut before it. So the installed launcher cannot start a 0.6.7 runtime.
    Needed: a build of HOI4-Mod-Setup main installed in place of that exe (or a v0.8.3 release).
    Without it, `--run-verified-meshy-mcp` would look for runtimes/meshy-0.6.2 and the 0.6.2 server
    has no meshy-t2.5 and the retired-model checks the contract expects.

0.2 The runtime folder %LOCALAPPDATA%/HOI4 Mod Setup/runtimes/meshy-0.6.7 (free, network = npm only).
    Source of truth: bootstrap_3d_workflow.ensure_meshy_runtime(). It checks the npm integrity of
    @meshy-ai/meshy-mcp-server@0.6.7, copies .tools/3d_pipeline/meshy_runtime/package.json and
    package-lock.json there, runs `npm ci --ignore-scripts --no-audit --no-fund --prefix <folder>`
    and requires the tree to hash to dbd2ebfce197a18875c3d367ad4b5325a345b92ce54c2a33440f5490efe7f6b3
    with 3,954 files. It calls no Meshy API and touches no Blender folder. Run only that function:
      py -3.13 -B -c "import sys; sys.path.insert(0, '.tools/3d_pipeline'); import bootstrap_3d_workflow as b; print(b.ensure_meshy_runtime(b.PIPELINE_ROOT, b.ensure_npx()))"
    (node 24.15.0 and npx are on PATH, so ensure_npx will not install anything.)
    Do NOT use the whole bootstrap or Setup's "Repair": see 0.5.

0.3 The launcher route in the worktree's .codex/config.toml (a local file write; do not commit it).
    MeshyClient reads [mcp_servers.meshy] from <repo>/.codex/config.toml and accepts only an
    absolute launcher outside the repository with args exactly ["--run-verified-meshy-mcp"].
    This worktree's config.toml has no such block. Free, one call:
      py -3.13 -B -c "import sys; from pathlib import Path; sys.path.insert(0, '.tools/3d_pipeline'); import bootstrap_3d_workflow as b; print(b.materialize_config(Path('.').resolve(), Path(r'C:/Users/klimp/AppData/Local/HOI4 Mod Setup/hoi4-mod-setup.exe')))"
    It appends the meshy, blender_hoi4 and (disabled) blender_lab blocks.

0.4 The Blender adapter route (free; writes only inside this worktree, all untracked or ignored).
    BlenderAdapterClient needs .tools/3d_pipeline/config/blender_hoi4_adapter.json, which only
    the bootstrap writes, and the adapter .venv. materialize_hoi4_adapter() does exactly that part:
    `uv lock --upgrade`, `uv sync --locked` in adapter/, then writes the config. It does not install
    anything into Blender. uv 0.11.14 is at C:/Program Files/Python313/Scripts/uv.exe.
      py -3.13 -B -c "import sys, os; from pathlib import Path; sys.path.insert(0, '.tools/3d_pipeline'); import bootstrap_3d_workflow as b; root = Path('.').resolve(); print(b.materialize_hoi4_adapter(root, b.PIPELINE_ROOT, b.ensure_uv(), Path(r'C:/Program Files/Blender Foundation/Blender 5.1/blender.exe'), {'install_root': os.environ['APPDATA'] + '/Blender Foundation/Blender/5.1/extensions/user_default/io_pdx_mesh'}))"

0.5 DECISION. Do not run the full bootstrap or Setup Repair on this machine without a decision.
    The installed io_pdx_mesh 0.91.0 does not match dependencies.lock.json: its three patched files
    (__init__.py, pdx_maya/maya_ui.py, pdx_blender/blender_import_export.py) hash differently from
    installed_patch_files_sha256, so ensure_io_pdx_mesh() would delete and replace the add-on in
    %APPDATA%/Blender Foundation/Blender/5.1/extensions/user_default, and the bootstrap also
    installs the Blender MCP add-on and starts its bridge. This phase forbids that. Steps 0.2 to 0.4
    avoid it; the cost is that exports in this experiment use the add-on as it is installed now (the
    same one the zin baseline was exported with, as far as the evidence shows).
